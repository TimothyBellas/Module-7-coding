# Semantic Search over Course Notes

This project searches the **eight supplied starter documents** in `docs/` (2,928 words, approximately six pages at 500 words per page). It loads `.txt` and `.md` files, divides them into overlapping passages, embeds them with `all-MiniLM-L6-v2`, and saves vectors plus text and source metadata in a persistent ChromaDB collection. The Streamlit page shows ranked passages, source filenames, cosine similarity and distance, and a rough relevance badge. It runs locally without a paid AI API key.

## Set up and run (Windows PowerShell)

Use **Python 3.12**, which was used to verify this project. Open PowerShell in the folder containing `semantic-search`, then run:

```powershell
cd semantic-search
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python ingest.py
python -m streamlit run app.py
```

The first ingestion downloads the Sentence Transformers model and may take a few minutes. Streamlit will print a local URL, usually `http://localhost:8501`. If `py -3.12` is unavailable, install Python 3.12 first or create the environment with an installed compatible Python version. On macOS or Linux, replace the environment commands with `python3 -m venv .venv` and `source .venv/bin/activate`.

The delivered `chroma_data/` contains the final experimental index (500-character chunks and 50-character overlap). Running `python ingest.py` resets it to the normal defaults (500 and 100) using your local dependencies. ChromaDB keeps the index across restarts. The generated database is ignored by Git; re-run ingestion after cloning a repository. Run commands from the `semantic-search` folder, although source paths within Python are resolved relative to the files.

## Try the interface

1. Ask **“How does FastAPI validate incoming data?”** and inspect the ranked passages, filenames, similarity and distance.
2. In the sidebar, choose **`fastapi.txt`** as the only source and search again. An empty source selection searches every file.
3. Raise **Minimum cosine similarity** to filter weak matches, or raise it far enough to see the empty state.
4. Change **Maximum results** and use **Re-index documents** to rebuild at different chunk size and overlap settings. The sidebar reports eight indexed documents and the active number of chunks.

The score is `1 - cosine distance`; it is a similarity value, **not** the probability that an answer is correct. The badge cutoffs are visual guides. A minimum similarity of zero disables the cutoff entirely. Empty or whitespace-only queries do not call the embedding model, and a source filter with no matching chunks returns an empty result.

## Project layout and architecture

| File | Responsibility |
| --- | --- |
| `docs/` | The eight starter text files, unchanged in subject and content. |
| `ingest.py` | UTF-8 loading, fixed character windows, batched local embeddings, and rebuilding the persistent Chroma collection. |
| `search.py` | Query embeddings, source filtering inside Chroma, distance filtering, ranking and index stats. |
| `evaluate.py` | Five labeled questions; source-level precision and recall; repeatable two-size experiment. |
| `app.py` | Streamlit controls, search results, metrics, empty states and re-index button. |
| `chroma_data/` | Persistent local index generated by ingestion. |
| `experiment_results.json` | Full top-three results with scores and relevance labels for both chunk sizes. |

Ingestion stores each passage with a stable `filename::chunk-N` ID and metadata `source`, `chunk_index`, `chunk_size`, and `overlap`. For a search, the same local model embeds the question; Chroma finds nearest vectors using **cosine distance** and applies any source filter before ranking. Re-indexing removes stale passages from the project collection when files or chunk settings change. The two experiment runs use identical documents, five queries, model, result count (**top three**), and overlap (**50 characters**); only chunk size changes.

## Evaluation and chunking experiment

Run the fixed five-query evaluation on the active index:

```powershell
python evaluate.py
python evaluate.py --n-results 5 --threshold 0.5
```

`--threshold` is a **maximum distance** (smaller is stricter), matching `search.py`. Recreate and print the complete two-size experiment:

```powershell
python evaluate.py --experiment
```

This builds a **200-character** index with overlap 50, evaluates it, then builds a **500-character** index with overlap 50 and evaluates again. It writes the complete ranked top-three hits, scores, relevance flags, and aggregate metrics to `experiment_results.json`. The final searchable index uses 500/50. To reset to the app's usual defaults afterward, run `python ingest.py`.

Relevance labels are **source filenames**, including two sources where both documents address a question. Precision is `relevant unique sources retrieved / unique sources retrieved`; recall is `relevant unique sources retrieved / all labeled relevant sources`. Repeated chunks from the same file count once for these metrics. The labels were defined for the five final questions before the reported comparison. A pilot with only straightforward, single-source questions retrieved the expected document every time, so the final set includes overlapping topics. This small set is illustrative rather than a general benchmark.

### Measured results on the supplied corpus

Verified with Python 3.12, ChromaDB 1.5.9, Sentence Transformers 5.7.0 and Streamlit 1.64.0. At 200 characters, ingestion produced **137 chunks**; at 500 characters, **49 chunks**. Both settings returned **average source precision 1.00** and **average source recall 0.90** over five queries. Each run retrieved the correct source for four questions with complete recall. The RAG and hallucination question retrieved `llms-and-ai.txt` three times but missed the also relevant `embeddings-and-vectors.txt`, giving recall 0.50 for that question at both sizes.

The table uses the highest ranked chunk's similarity as a **secondary tie-breaker** when source precision and recall match. The full top-three sources, scores and relevance marks for each row are in `experiment_results.json`.

| Question (shortened) | 200-char top score | 500-char top score | Better by top score | Source-level observation |
| --- | ---: | ---: | --- | --- |
| Python virtual environments | 0.511 | 0.490 | 200 | Both returned `python-fundamentals.txt` and had full recall. |
| API validation and HTTP errors | 0.526 | 0.520 | 200, narrowly | Both found `rest-apis.txt` and `fastapi.txt` in the top three. |
| SQLAlchemy and FastAPI dependencies | 0.614 | 0.628 | 500, narrowly | Both found `sql-databases.txt` and `fastapi.txt`. |
| Streamlit reruns and widget state | 0.572 | 0.640 | 500 | Both returned `streamlit.txt` and had full recall. |
| Vector retrieval and LLM hallucinations | 0.409 | 0.414 | 500, narrowly | Both found only one of two labeled sources. |

**Conclusion:** By the primary source-level metrics, the sizes tie. The 500-character setting has a slightly higher mean top-hit similarity (**0.538 vs. 0.526**), retains more surrounding explanation per result, and uses fewer chunks; it is the chosen default for this small corpus. The clearest difference is the Streamlit question, where 500 characters increased the top score from 0.572 to 0.640. Shorter windows helped the precise Python question. The RAG question shows a limitation of ranking chunks alone: near-duplicate hits from one source can crowd out another relevant source. Source diversification or paragraph-aware chunking could improve that case. Five questions are too few to establish a universal best chunk size, and source-level labels do not assess whether every retrieved passage answers the whole question.

## Modify the corpus

Add UTF-8 `.txt` or `.md` files in `docs/`, then click **Re-index documents** or run `python ingest.py --chunk-size 200 --overlap 50`. Update `EVAL_SET` in `evaluate.py` if the expected relevant filenames change. Indexing requires a nonempty document folder and a valid chunk size greater than its overlap.
